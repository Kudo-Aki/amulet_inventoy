# 個人アカウントから Google Workspace への移行ガイド

個人の Google アカウント（`@gmail.com`）で作った GAS バックエンドを、Google Workspace アカウントへ移す手順です。

---

## 0. 結論から

| 疑問 | 答え |
|---|---|
| Workspace アカウントで動くか | **動きます。** コードにアカウント固有の値は一切ハードコードされていません |
| スクリプトを共有して複製すれば済むか | **済みません。** スクリプトプロパティ・トリガー・デプロイ・OAuth承認は複製で引き継がれません |
| デプロイは作り直しが必要か | **必須です。** `/exec` URL は必ず変わり、全端末の設定を貼り替えることになります |
| 所有権を移せばよいのでは | **できません。** 個人アカウント ↔ Workspace アカウント間の Drive 所有権移転は Google がサポートしていません（※要確認・後述） |
| コードの変更は必要か | **不要です。** リポジトリの `gas/` をそのまま使えます |

**推奨するやり方は「共有して複製」ではなく「Workspace 側で空のプロジェクトを作ってリポジトリから貼る」です。**
`gas/` に必要な7ファイルすべてが入っているので、旧プロジェクトを一切触らずに済み、旧環境が退避先として丸ごと残ります。

### 引き継がれるもの / 引き継がれないもの

| 対象 | 引き継がれるか | 移行作業 |
|---|---|---|
| `.gs` のコード | ○ | リポジトリから貼る |
| `appsscript.json`（timeZone、Drive v2 宣言、webapp 宣言） | ○ | **必ず一緒に貼る**（後述の v2/v3 問題） |
| スクリプトプロパティ `OMAMORI_SPREADSHEET_ID` | **×** | 手で登録。**移行の最初の1手** |
| インストール型トリガー4本 | **×** | `setupFormIntegration()` を1回実行 |
| ウェブアプリのデプロイ / `/exec` URL | **×** | 新規デプロイ → 全端末を貼り替え |
| OAuth 承認 | **×** | 初回実行時に承認 |
| スプレッドシート・フォーム4つ・ラベルPDFフォルダ・Slidesテンプレート | **×**（別の Drive ファイル） | 下記の手順 |
| 「設定」シートの自動設定14キー | スプレッドシートをコピーすると**旧アカウントのIDが残る** | **setup 前に空にする**（最大の事故ポイント） |

## 1. 着手前の判定（ここが通らないと計画が変わります）

**先に 20 分だけ使ってここを確かめてください。** 本番の移行作業を始めてから気づくと手戻りが大きいです。

### 1-1. ウェブアプリを匿名で公開できるか ← 最優先

このアプリは GitHub Pages の静的ページから、ブラウザが**ログインなしで** `/exec` を `fetch` する設計です
（`js/api.js`）。`gas/appsscript.json` も `"access": "ANYONE_ANONYMOUS"` を宣言しています。
ここが塞がれていると、トリガーもフォームも正常なのに**アプリ全体が動きません**。
「とりあえず組織内のみで公開」という妥協は取れません（未ログインの fetch がログイン画面へ飛ばされ、CORS エラーで全APIが死にます）。

**確かめ方**

1. Workspace アカウントで**空のスクリプト**を新規作成し、次を貼る

   ```js
   function doGet() {
     return ContentService.createTextOutput(JSON.stringify({ ok: true }))
       .setMimeType(ContentService.MimeType.JSON);
   }
   ```

2. 「デプロイ」→「新しいデプロイ」→ ウェブアプリ →
   次のユーザーとして実行: **自分**／アクセスできるユーザー: **全員**
3. **シークレットウィンドウ**（ログインしていない状態）でその `/exec` URL を開く

`{"ok":true}` が表示されれば合格です。
**デプロイ画面に「全員」の選択肢が出たことは合格の証明になりません。** 必ず未ログインで開いて確認してください。

> **通らなかった場合**（組織のポリシーで塞がれている）
> あなたは管理者なので、管理コンソールで該当の設定を緩めれば開けられる可能性があります。
> どうしても開けない場合は、GitHub Pages をやめて GAS 側で画面を返す（`HtmlService`、同一オリジン、
> アクセス範囲を組織内に）構成に変える必要があります。ただし**フォームの回答者に組織外の方がいる場合、
> フォーム側は別途「組織外からの回答」を許可する必要があります**。

### 1-2. フォームが組織外から回答を受け取れるか

入荷・出荷・棚卸・商品登録の4フォームは、現場の方に匿名で回答してもらう前提です
（`setCollectEmail(false)` / `setLimitOneResponsePerUser(false)`）。

Workspace では、組織所有のフォームが組織外から回答を受け取れるかを**管理者が制御できます**。
回答者に組織外の方（アルバイト、巫女、外部の方）が含まれる場合、ここを許可しておく必要があります。

管理コンソール → アプリ → Google Workspace → ドライブとドキュメント のあたりに
フォームの回答に関する設定があります。**設定名と場所は Google の仕様変更で動くため、
「Forms」「回答」で管理コンソール内を検索してください。**

### 1-3. 管理コンソールで3点確認（各1分）

| 設定 | オフだとどうなるか |
|---|---|
| **Google Apps Script**（アプリ → Google Workspace → ドライブとドキュメント） | ウェブアプリもトリガーも一切動きません。既定はオン |
| **Drive SDK**（ドライブとドキュメント → 機能とアプリケーション） | Drive API を使う処理が落ち、**ラベルテンプレートの生成**（`gas/LabelPdf.gs`）と**起案書作成**（`gas/Code.gs`）が失敗します |
| **API の制御 / アプリのアクセス制御**（セキュリティ → アクセスとデータ管理） | 厳しい設定だと OAuth 承認自体がブロックされます。「内部のドメイン所有アプリを信頼する」を有効にすれば解消します |

> **安心材料**: 自組織が所有する内部アプリなので Google の OAuth 審査（verification）は不要です。
> 「このアプリは確認されていません」の警告に悩む必要はありません。
> また `executeAs: USER_DEPLOYING` なので、**フォームの回答者やアプリの利用者に同意画面は一切出ません**。
> 承認するのはデプロイしたあなた1人だけです。

## 2. 旧環境の整理（**課金の解約より先に**）

> **順番が重要です。** 先に Google One を解約すると容量超過で旧ファイルが読み取り専用になり、
> この章の作業自体ができなくなります。

### 2-1. 未処理の回答をゼロにする

旧アカウントの Apps Script エディタで `processPendingResponses()` を実行し、
各回答シートの「処理結果」列が空の行が無くなったことを確認します。

*理由: 未処理のまま移行すると、後述の `_旧` シート退避によって永久に処理されなくなります。*

### 2-2. 旧フォーム4本の受付を止める

各フォームを開き、「回答」タブの「回答を受け付けています」をオフにします。
閉鎖メッセージに新しいフォームの案内を入れておくと親切です。

*理由: 現場の貼り紙やブックマークに旧 URL が残ります。これが**最も起こりやすい無言失敗**の原因です（後述）。*

### 2-3. 旧アカウント自身でトリガーを全削除する

旧アカウントのエディタで「トリガー」（時計アイコン）を開き、4本すべて削除します。
`ScriptApp.getProjectTriggers().length` を実行して `0` になることを確認してください。

> **これは本人しかできません。** トリガーは「スクリプト × 作成したユーザー」単位で、
> **他のアカウントからは見ることも削除することもできません。** 移行後に気づいても手遅れになります。

*理由: 旧トリガーを残すと在庫が二重計上され、しかも冪等ガードが効きません（後述）。*

### 2-4. 退避用のコピーを取る

1. Drive でスプレッドシートを右クリック → 「コピーを作成」（移行とは別に、手元の退避用）
2. 各フォームの「回答」タブ → スプレッドシートアイコンの隣の︙ → 「回答をダウンロード（.csv）」

*理由: アプリ内蔵のバックアップ機構は**商品管理シートのA〜K列だけ**が対象です。
箱台帳・履歴・入力者・設定シートは対象外で、フォーム側の生の回答は旧アカウントを消すと復元できません。*

## 3. 新環境の構築

### 3-1. スプレッドシートを Workspace 側に用意する

Drive でスプレッドシートを**コピー**し、Workspace アカウントのマイドライブに置きます。
（旧アカウントから Workspace アカウントへ共有 → Workspace 側で「コピーを作成」）

新しいスプレッドシートの**ID**（URL の `/d/` と `/edit` の間の長い文字列）を控えてください。

> コピーすると**フォームとのリンクは切れます**。回答シートはただのデータとして残ります。
> これは好都合です（後述の「無言失敗」の節を参照）。

### 3-2. 空のスタンドアロンプロジェクトを作ってコードを貼る

[script.google.com](https://script.google.com/) で「新しいプロジェクト」。
リポジトリの `gas/` から次を同名で追加し、全文を貼ります。

| ファイル | 追加方法 |
|---|---|
| `Code.gs` | 既定で作られる `コード.gs` を `Code.gs` にリネームして貼る |
| `FormIntegration.gs` / `LabelPdf.gs` / `LabelTemplate.gs` / `QRCode.gs` / `Tests.gs` | 「＋」→「スクリプト」→ 名前を入力して貼る |
| `appsscript.json` | 歯車「プロジェクトの設定」→「`appsscript.json` マニフェスト ファイルをエディタで表示する」にチェック → 開いて貼る |

> **`appsscript.json` を必ず貼ってください。** ここに Drive API **v2** の宣言が入っています。
> エディタの「サービス」から手で Drive を追加すると **v3 が既定で選ばれ**、
> コードが使っている `Drive.Files.insert` が存在せず（v3 は `Files.create`）ラベル生成が壊れます。

### 3-3. ★最初の操作: スクリプトプロパティを登録する

歯車「プロジェクトの設定」→ 下部「スクリプト プロパティ」→「スクリプト プロパティを追加」

| プロパティ | 値 |
|---|---|
| `OMAMORI_SPREADSHEET_ID` | 3-1 で控えた新しいスプレッドシートのID |

> ### `initializeSpreadsheet()` は実行しないでください
>
> この関数は**新規構築用**です。新しい空のスプレッドシートを作ってこのプロパティを上書きするため、
> アプリが既存データを見られなくなります。
>
> 現在のコードは、プロパティに有効なIDが入っていてUIが無い（＝スタンドアロン実行）場合に
> **作成せず理由を示して停止する**ようになっています。それでも触らないのが安全です。
> 別のスプレッドシートに切り替えたいときは、このプロパティの値を直接書き換えてください。

### 3-4. どのスプレッドシートを掴んでいるか目で確認する

関数 `getSpreadsheetUrl` を選んで実行します。初回はここで OAuth 承認を求められるので許可してください。
実行ログに出た URL が 3-1 で作ったスプレッドシートであることを確認します。

*理由: これが「正しいブックに繋がっている」ことの最短の検証です。*

### 3-5. ★「設定」シートのID類を空にする

新しいスプレッドシートの「設定」シートを開き、次の**15個の「値」セルを空に**します。
キーの行は消さず、B列（値）だけを空にしてください。

| 空にするキー | 理由 |
|---|---|
| `inFormId` / `inFormUrl` / `inFormEditUrl` | 旧アカウントのフォームを指しているため |
| `outFormId` / `outFormUrl` / `outFormEditUrl` | 同上 |
| `invFormId` / `invFormUrl` / `invFormEditUrl` | 同上 |
| `productFormId` / `productFormUrl` / `productFormEditUrl` | 同上 |
| `driveFolderId` | 旧アカウントのラベルPDFフォルダを指しているため |
| `labelTemplateId` | 旧アカウントのSlidesテンプレートを指しているため |
| `adminEmail` | 空にしておくと Workspace のアドレスが自動で入ります |

> ### ここを飛ばすと何が起きるか
>
> `setupFormIntegration()` は単にトリガーを置くだけの関数ではありません。
> **アクセスできないIDを見つけたら黙って作り直して設定シートを上書きする自己修復関数**です。
> しかも「権限がない」と「IDが無効」を区別しません（`openFormIfExists_` が全例外を `null` に落とすため）。
>
> - **旧フォームに閲覧権が残っている場合**: setup の最後に走る `syncFormChoices()` が
>   **旧フォームの選択肢を上書きします**。退避先として生かしておきたい旧フォームが壊れます
> - **旧フォームに権限がない場合**: フォーム4つが新規作成され、設定シートのIDが全部書き換わり、
>   旧フォームは参照されない「孤児」になります

あわせて `dailyBackupHour`（毎日バックアップの時刻）をこの時点で決めてください。
`ensureTriggers_` はハンドラ関数名しか照合せず**既存トリガーの時刻を更新しないため、setup は1回勝負**です。

### 3-6. `setupFormIntegration()` を1回だけ実行する

実行ログに次が出れば成功です。

```
設定シート: OK
入力者シート: OK
箱台帳シート: OK
ラベルPDFフォルダ: https://drive.google.com/...
ラベルテンプレート: OK
バックアップ台帳・明細シート: OK
入荷フォーム: https://docs.google.com/forms/...
出荷フォーム: https://docs.google.com/forms/...
棚卸フォーム: https://docs.google.com/forms/...
商品登録フォーム: https://docs.google.com/forms/...
トリガー: OK（onFormSubmit / syncFormChoices 毎日6時 / processPendingResponses 10分毎 / dailyBackupJob）
```

次のどちらかが出ていたら対処してください。

| ログ | 意味と対処 |
|---|---|
| `ラベルテンプレート: 要確認 → ...` | Drive API 経路が失敗しています。1-3 の Drive SDK を確認して再実行 |
| `★未公開です（このままでは回答を受け付けません）` | フォームを開いて手動で公開してください |

### 3-7. 新しいデプロイを作る

「デプロイ」→「新しいデプロイ」→ ウェブアプリ →
次のユーザーとして実行: **自分**／アクセスできるユーザー: **全員** →「デプロイ」。
表示される `/exec` で終わる URL を控えます。

> **setup の実行とデプロイは必ず同じ Workspace アカウントで行ってください。**
> ウェブアプリの実行者は「デプロイした人」、トリガーの実行者は「トリガーを作った人」です。
> 別アカウントだと権限・メールの差出人・Gmail下書きの保存先が経路ごとに食い違い、
> 管理画面のトリガー表示も「未設置」と誤表示されます。

> `/exec` で終わる URL を使ってください。実行後に `script.googleusercontent.com/macros/echo...` に
> 飛ばされることがありますが、そちらは一時的なリダイレクト先なのでアプリに貼ってはいけません。

## 4. 受け入れテスト（**画面の成功表示で判定しないこと**）

### 4-1. シークレットウィンドウで4フォームから実際に送信する

管理画面「API設定」→「Googleフォーム連携」で各フォームのURLを開き、**未ログイン状態**で1件ずつ送信します。

そのうえで **スプレッドシートの行を直接見て** 反映を確認してください。

> ### 「保存しました」は証拠になりません
>
> デプロイのアクセス範囲が「全員」になっていないと、GAS はログイン画面の HTML を返します。
> 現在のコードは**その場合にエラーを出す**ようになりましたが（原因のヒント付き）、
> フォームからの送信はサーバー側で完結するため、画面では何も分かりません。
> **必ずシートを見てください。**

4フォームそれぞれから送るのは手間ですが、**スプレッドシートに紐づく `onFormSubmit` トリガーが
4フォームすべてで発火することの公式な保証文は見つけられませんでした**（※要確認）。
1本ずつ実測するのが唯一確実な確認方法です。

### 4-2. ★箱番号を旧新で突き合わせる

箱台帳シートで、商品ごと・年ごとの `boxNumber` の最大値が旧環境と一致することを確認します。

**ここが一致するまで入荷フォームを現場に公開しないでください。**
台帳が空だと `0001` から振り直し、**既に印刷して箱に貼ったラベルと番号が衝突**します。
台帳シートは無ければ自動で作られる（＝空で作られる）ので、気づきにくい事故です。

### 4-3. ラベルPDFの経路を確認する

`test_sampleLabelPdf()` を実行し、ログに出た PDF を開きます。
Drive v2 → Slides → PDF → メール添付の一連が通ることの確認です。
ラベルPDFメールの差出人が Workspace のアドレスになっていることも見てください。

### 4-4. 棚卸と復元の往復を1回やる

1. 棚卸フォームから1件送信 → 在庫が数えた数になり、回答シートの「バックアップ」列にIDが入る
2. 管理画面「バックアップと復元」でそのIDを選び、「変更点を確認」→「この内容で復元」→ 在庫が戻る

**これができれば「間違えても戻せる」状態が整ったことになります。** 移行後に最初に確認すべき1項目です。

### 4-5. メール送信の余裕を実測する

`MailApp.getRemainingDailyQuota()` を実行して値を記録します。
トライアル中や支払い実績が浅いドメインでは公称値より低く絞られることがあります。

### 4-6. 流して安全な確認用関数

| 関数 | シートへの影響 |
|---|---|
| `test_hasAnswer` / `test_productCode` / `test_formSpecs` / `test_parseDataParam` / `test_parseLabelRange` / `test_consumeDeliveries` | なし |
| `test_dryRunLastInRow` | なし（解釈だけ） |
| `test_sampleLabelPdf` | Drive に PDF が1つ増えるだけ |
| **`test_backupRoundTrip`** | **商品管理シートを一時的に書き換えます**（最後に元へ戻します）。本番データでは流さないでください |

## 5. 切り替えと退役

### 5-1. 全端末の URL を貼り替える

管理画面「API設定」の「QRコード生成」タブで新しい `/exec` URL の QR を表示し、
**全部のスマホ・全部のブラウザ**で読み取って設定し直します。

> API URL は `localStorage` に端末ごと独立に保存されています。1台直しても他は直りません。
> **貼り替えが終わるまで誰にも入力させないでください。** 貼り替え後は一度リロードしてください。
> （サービスワーカーは使っていないので「古い JS が残る」心配はありません）

### 5-2. 現場の貼り紙・ブックマークを差し替える

倉庫に貼ったフォームのQRコードを新しいものに差し替えます。
`docs/manual.md` にも「倉庫に貼ってあることもあります」と書いてある通り、ここが残りがちです。

### 5-3. 旧環境を閉じる

1. 旧プロジェクトのデプロイを「デプロイを管理」からアーカイブ
   *理由: 旧デプロイは「全員」公開のままなので、URLを知っている端末から呼ばれ続けます*
2. 旧ラベルPDFフォルダ・旧スプレッドシートの共有を解除

### 5-4. 最後に Google One を解約する

解約前に旧アカウントの Drive を `owner:me` で検索し、移し忘れがないことを確認してください。

## 6. 移行で気をつけるデータ

### 旧フォームURLからの回答は「完全な無言失敗」になります

旧フォームが生きていて、旧スプレッドシートも生きている場合:

- 旧フォームへの回答は**旧スプレッドシートに入り続けます**
- 旧アカウントのトリガーを削除済みなら、その行は**誰にも処理されません**
- **在庫反映なし・ラベルPDFなし・エラーメールもなし。** 送った人は成功したと思っています

**2-2（旧フォームの受付停止）と 5-2（貼り紙の差し替え）は必須です。**

### `_旧` シートは触らないでください

同じスプレッドシート内でフォームを作り直した場合、既存の `フォーム回答_入荷` 等は
`フォーム回答_入荷_旧yyyyMMddHHmm` にリネームされて退避され、新しい空のシートが作られます。

退避された `_旧` シートの行は `onFormSubmit` も `processPendingResponses` も触りません（シート名が一致しないため）。
これは正しい動作ですが、**`_旧` シートの「処理結果」列を人が消すと再処理されて在庫が二重反映されます。**
シート保護をかけておくのが安全です。

### 旧トリガーを残すと冪等ガードが効きません

- トリガーは**作成者本人にしか見えません**。`ensureTriggers_` は `getProjectTriggers()` で既存を数えるため、
  **旧トリガーが生きていても「0本」と誤認して全部作ります**
- さらに `LockService.getScriptLock()` は**スクリプトプロジェクト単位**です。
  旧プロジェクトと新プロジェクトは別のロック空間になるため、
  「ロック取得 → 処理結果が空か確認 → 処理中を書く」という冪等ガードが**無効化されます**。
  両方が「処理結果が空」と読んで在庫を二重加算し得ます
- 加えて `gas/Code.gs` の書き込み系（`saveStockToProducts` など）は**ロックを取っていません**

**旧トリガーの削除（2-3）は「推奨」ではなく「切り替えの前提条件」です。**

### トリガー失敗の通知はトリガー作成者にしか届きません

インストール型トリガーの失敗は画面に出ず、**トリガーを作ったアカウント宛のサマリーメール**でしか通知されません。
移行直後しばらくは、旧アカウントの受信も見ておいてください。

### メールの差出人が変わります

コードは表示名（`mailSenderName`）しか設定しておらず、**実際の差出人は実行アカウント**です。
ラベルPDFメール・在庫警告・管理者通知の送信元が Workspace のアドレスに変わるので、
受信側の振り分けルールや許可リストを見直してください。
見積依頼の Gmail 下書きも **Workspace 側のメールボックス**に作られます。
「設定」シートの署名項目（`orgName` / `senderName` / `senderEmail` など）も更新してください。

### 失われないもの（心配しすぎなくてよい点）

| 対象 | 理由 |
|---|---|
| **既に印刷したラベル・箱のQR** | QRの中身は `HEALTH-26-0007` という文字列だけで URL を含みません。**刷り直し不要** |
| ラベル用 Slides テンプレート | `LabelTemplate.gs` に同梱された元データから自動再生成されます（`labelTemplateId` を空にして setup するだけ） |
| ラベルPDF保存フォルダ | 自動作成されます |
| 箱番号の「年」 | `Asia/Tokyo` が直接指定されているので、タイムゾーン設定に影響されません |
| 署名・入力者・発注先の情報 | すべて「設定」「入力者」「商品管理」シートにあり、コードには含まれていません |
| 管理画面のフォームURL表示 | 設定シート経由で自動反映されます。手作業はありません |

### 移行で良くなること（クォータ）

| 項目 | 個人アカウント | Workspace |
|---|---|---|
| メール送信（受信者数/日） | 100 | 1,500 |
| トリガーの合計実行時間/日 | 90分 | 6時間 |
| ドキュメント作成数/日 | 250 | 1,500 |
| スクリプト1回の実行時間 | 6分 | 6分（**変わりません**） |

`processPendingResponses` が10分毎（144回/日）＋ `syncFormChoices` ＋ `dailyBackupJob` ＋ `onFormSubmit`
という構成では、個人アカウントの90分/日は**1回平均37秒**しか使えず枯渇しやすいので、ここは明確な改善です。

**※この数値は一次情報で確認できていません（要確認）。** 実運用前に
`MailApp.getRemainingDailyQuota()` の実測（4-5）で確かめてください。
また「6分/実行」の壁は変わらないので、既存の分割処理の設計は維持してください。

## 7. 確認できなかったこと

このガイドを書いた環境から Google の公式ドキュメントに接続できなかったため、
以下は**二次情報に基づく推測を含みます**。断定していません。

| 項目 | 状況 | 対処 |
|---|---|---|
| ウェブアプリの「全員（匿名ユーザーを含む）」を管理者設定で塞げるか | 二次情報は一致するが公式記述を確認できていない | **1-1 の実機確認が唯一確実な判定です** |
| フォームの「組織外からの回答」設定の正確な場所と既定値 | 設定の存在は複数の情報が一致。場所は仕様変更で動く | 管理コンソールで「Forms」「回答」を検索 |
| API 経由で作ったフォームが未公開状態になるルール | Forms API では明記。`FormApp.create()` に及ぶかは不明 | コード側で明示的に公開済み。4-1 で実際に送信して確認 |
| クォータの具体値 | 広く知られた値だが一次情報未確認 | 4-5 で実測 |
| スプレッドシートに紐づく `onFormSubmit` が複数フォームすべてで発火するか | 公式はスプレッドシート単位の表現のみ | 4-1 で4フォームそれぞれから送信して確認 |
| 個人アカウント → Workspace の Drive 所有権移転 | 現行ヘルプは「不可」と記述（2026年時点） | コピーで移す前提の手順にしてあります |
| フォーム連携済みのスプレッドシートをコピーしたとき、コピー側がフォームとのリンクを保持するか | 未確認 | 3-1 の後、回答シートが更新されないことを確認 |
| 既存フォームの回答先だけを新スプレッドシートに変更した場合、過去の回答が新シートに流し込まれるか | 未確認。流し込まれると「処理結果」列が空のため**二重計上の危険** | **この方法は使わず、フォームは作り直してください** |

## 8. 困ったとき

| 症状 | 確認 |
|---|---|
| アプリが「APIの応答を解釈できませんでした」と出る | デプロイの「アクセスできるユーザー」が「全員」か。URL が `/exec` で終わっているか |
| 管理画面に「フォーム連携の情報を取得できませんでした」と出る | GAS を**新しいバージョン**でデプロイしたか |
| フォームカードが2枚しか出ない | `setupFormIntegration()` を実行したか。設定シートの `invFormId` / `productFormId` が入っているか |
| フォームを送っても在庫が変わらない | 回答シートの「処理結果」列を確認。空なら管理画面の「未処理の回答を再処理」。旧フォームに送っていないか |
| ラベルPDFが届かない | `test_sampleLabelPdf()` を実行。失敗するなら Drive SDK（1-3）とメール送信上限を確認 |
| 箱番号が 0001 に戻った | 箱台帳シートが空。旧環境からコピーし直してください（4-2） |

通常の運用については [google_form_guide.md](google_form_guide.md) を参照してください。
